# Develop

**Status:** v0.1, a first version to try. It runs sessions, shows which need you, stops idle ones, keeps follow-ups that haven't started, and tracks each session's GitHub PR and its Depot CI run. Waits on a time, another session, a PR's checks, reviews, approval, or merge, or a PostHog deploy resolve themselves. Messages can carry dropped or pasted images. It groups sessions, sends one message to a group, and reads and updates plan documents attached to a group, with model-written status updates that wait for your approval. Each group can have a chat, a Claude session that manages only that group's sessions. The design plan is in `~/dev/haacked/notes/Dev/repositories/haacked/switchboard/plans/switchboard.md`, and v0.1's scope is in `plans/v0.1-app.md` next to it.

```
bin/build           # swift build with bin/test's flags; extra arguments go to swift build
bin/test            # the tests that the files changed against origin/main can affect, and never all of IntegrationTests, which CI runs on every push; builds only the test bundles that hold them, and prints what it picked and why
bin/test --all      # every unit test, and integration tests that run a private sbd against a stub claude; only for reproducing a CI failure
bin/test --claude   # also the tests that run the installed claude with Haiku, in about 4 minutes
bin/test-gui        # runs the app in a hidden window, checks the bytes its terminal sends, that sessions survive an app relaunch, message drafts, and drops on the message field; needs a logged-in Mac session
bin/test-gui drops  # runs only the named checks: terminal, relaunch, drafts, drops
bin/measure         # starts 25 and then 50 stub sessions on a private sbd and prints memory and `sb ls` times
bin/measure --running  # prints the memory of the sbd that runs now, with its real claude processes; starts and stops nothing
bin/fmt             # formats Sources, Tests and Package.swift with swift format; --check lists files that differ and exits 1
bin/bundle          # build/Switchboard.app
bin/icon            # re-renders assets/icon/AppIcon.icns from AppIcon.svg after you edit it; needs rsvg-convert
bin/screenshots     # redraws the README's images in docs/images from made-up sessions, in a hidden window; `bin/screenshots board` draws one
```

To see a view change, build only the app and draw one image from the build you just made: `bin/build --product Switchboard && bin/screenshots --bin "$(swift build --show-bin-path)" --out .notes/shots board`. After an edit to one view file, the build takes about 8 s and `bin/screenshots` takes about 12 s, 6 s of which is the app's delay before it draws. The PNG lands in `.notes/shots/board.png`. Without `--out`, the script overwrites the README's image in `docs/images`. Name a different image to see another screen: `hero`, `inbox-permission`, `board`, `group-chat`, `accounts`, `session-panel`, or `search`. Plain `bin/screenshots board` also builds `sbd` and `sb`, which a view edit does not change. To put the app into another state, launch the built `Switchboard` with the `SB_*` hooks that `Sources/SwitchboardApp/Snapshot.swift` lists, such as `SB_SNAPSHOT=<png>` and `SB_SELECT=<session id>`. The recipe rebuilds only the app, but `--bin` also runs the `sbd` and `sb` in that folder, and it stops with `no sbd in …` when they are missing. After a Core or Service edit, or in a worktree that has not built `sbd` and `sb` yet, run plain `bin/screenshots --out .notes/shots board`, because `sbd` links Service and Core and `sb` links Core. Run `bin/test` only to check behavior, because it builds the test bundles too.

`bin/test` builds only the test bundles that its selection names, each in its own `swift build --product <bundle>`, and then runs with `--skip-build`. A bundle that it does not build keeps its last build, so every `--filter` names only a target whose bundle it just built. The selection already names every test target that depends on a changed target, so a Core source edit builds the Core, Service, and App test bundles and leaves IntegrationTests to CI. An edit to one Core test file builds only `SwitchboardCoreTests`. `swift test --skip-build` fails when any test target's bundle is missing, so `bin/test` builds every bundle when a test target has no bundle of its own in the build folder. That happens on the first run in a new worktree, and on every run with Swift before 6.4, whose native build system makes one bundle for all test targets. `bin/test --all` and the runs that CI starts build every bundle.

`bin/test --filter <pattern>` also builds only the bundles that can hold a matching test, then runs with `--skip-build` and a `--skip` for each bundle it did not build. A pattern that starts with `^<target>\.`, holds after that only names, `/`, `\.`, `|`, and parentheses, and has no `|` outside parentheses, such as the patterns that `bin/test` prints, builds that target's bundle. A bare name such as `AgoTests` builds each test target whose name, file paths, or source text contain it, so `bin/test --filter AgoTests` builds only `SwitchboardCoreTests`. Any other pattern, filters that every bundle could match, and any argument besides `--filter` run plain `swift test`, which builds every bundle in one build.

`bin/build`, `bin/test`, `bin/bundle`, and the builds in `bin/test-gui`, `bin/measure`, and `bin/shard-weights` wait for a machine-wide build slot (`bin/lib/build-slot`), so many worktrees can build without overloading the CPU. At most 3 hold a slot at once, and the rest wait in the order they arrived and print `waiting for a build slot (N ahead)`. `bin/test` holds one slot for its build and its tests. `bin/test --shards N` takes one slot for its build and one for each shard, so each `swift test` process that runs tests counts against the limit. Sharding is for CI, and `bin/test --shards N` prints a warning when `CI` is not `true`, unless `--force-shards` follows the count. `bin/test` prints the slot and job limits in effect when it starts. A slot frees when its holder exits, even from `kill -9`. Each compiling `swift build` and `swift test` runs with `--jobs 4`, or the CPU count when that is lower (`bin/lib/swiftpm`). `SB_BUILD_SLOTS` sets the slot count, and `0` turns the queue off. `SB_BUILD_JOBS` sets the job count, and `0` lets SwiftPM start one job per core. `SB_BUILD_SLOTS_DIR` moves the queue's folder from `~/Library/Caches/Switchboard/build-slots`. That folder must hold only the queue's files, because the helper deletes its own stale temp files there and overwrites its `mutex` and `counter` files.

Integration suites declare `.blocking(timeLimit:)` in place of `.timeLimit`. Each test waits for a free slot without holding a thread, and its time limit starts once it has the slot. One test process runs 4 such tests at once, or one fewer than there are CPUs when that is lower. `SB_TEST_SLOTS` sets another count, and a count above one fewer than the CPUs counts as that, which keeps one of Swift's pool threads free for async tests. The count applies to each test process, so `bin/test --shards N` runs up to N times as many at once. A test that starts a private `sbd` in a suite without the trait records an issue. App tests build `BoardModel` with `offlineModel()`, whose client finds no `sbd`, so a test never reads the sessions of the `sbd` you run.

## Prompts

The text that a model reads as a prompt or a guide lives in `prompts/<name>.md`, not in Swift: the Manager guide and the operator's role (`manager-guide.md`, `operator.md`), the group chat guide, the triage card format that `sb summary help` prints, and the system prompts of the summarizer, the skill classifier, the merge brief, the quick ask, the top-up pick, the operator's judge, the session namer, plan updates, and the Slack thread poll's thread read and user id lookup (`slack-threads.md`, `slack-self.md`). The `Prompt` enum in `Sources/SwitchboardCore/Prompts.swift` lists them. Each file is the exact text, minus the newline that ends the file. `{{key}}` marks a value that code fills, such as a length limit or the text of `ChildQuestions.guidance`. `Prompt.values` says which keys a file must name. A file that names another key, or leaves one out, stops sbd with an error that names the file.

To change a prompt, edit the file and restart sbd. Nothing recompiles. Where sbd looks, in this order:

- `SB_PROMPTS_DIR`, when it is set.
- `Contents/Resources/Prompts` of the Switchboard app that holds the sbd. `bin/bundle` copies `prompts/` there and ends by running `sbd --check-prompts` on the bundle, so a bundle without its prompts fails to build. `bin/install` and `bin/update` ship the bundle, so an installed sbd reads the copy in the installed app. To change an installed prompt, run `bin/install`.
- `prompts/` in the checkout that compiled the sbd, for an sbd that SwiftPM built. Run the checkout's sbd, such as `.build/debug/sbd --home /tmp/sb-try`, edit a file, and restart it.

A missing or unreadable file stops sbd at start with an error in `sbd.log` and no fallback. A copy of the text compiled into the binary would give a stale prompt after a broken install, and nobody would see it. The tests read the same files through `Prompts.text`, so a test cannot pass against a copy.

The app draws its terminals with SwiftTerm.

`bin/test-gui` runs the app's `TerminalSelfTest` (`SB_TERMINAL_TEST`) against a private `sbd` whose `claude` is `Tests/GUI/received-bytes-stub`, a stand-in that shows every byte it receives. The test sends keys, a paste, a scroll, and a resize to the Claude pane, and then compares the bytes that `sb screen` shows with the expected ones. It opens a real window that it hides, so it needs a logged-in macOS session with a display, and it refuses to run from an SSH or background session (`SB_GUI_ANY_SESSION=1` tries anyway). It uses a short `SB_HOME` under `/tmp`, because a Unix socket path cannot exceed 103 bytes, and ends the app, `sbd`, tmux, and the stand-in and deletes the folder when it exits, even when it fails. It leaves the app's log, the final screen, and the pane PNGs in `.build/gui-test/terminal`, and after any failure also the `sbd` log in `.build/gui-test/sbd.log`. Before it sends keys, the self test waits up to 180 s until the session reports a tmux client on its Claude pane, the window holds a terminal view, and `bin/test-gui` has seen the stand-in take the app's size. It then checks that a session keeps running when the app quits or is killed. It types into the stand-in and the session's shell, quits the app (`SB_QUIT_FILE`, which makes the app quit as ⌘Q does), and compares the session record, both panes' pids, and the stand-in's screen before and after, with the app gone and again once a new app has attached. It then does the same after `kill -KILL` of the app, and checks that the shell is the same process. Last, through the app's `ShellSelfTest` (`SB_SHELL_TEST`), it closes the shell of the Manager, a work session, an Inbox item, and a chat with the pane's close button, `exit`, Ctrl-D, and the Session menu. It checks that the shell stays closed after a relaunch and a switch to another session, and that the Claude terminal keeps its tmux client throughout. It also sends ⇧⌘], ⇧⌘[, ⌘L, ⌘T, ⌘[, ⌘], ⌘Y, and ⌘K to the menu bar as a US keyboard types them, and checks that each reaches its menu item. It checks that File holds New Loop…, that View holds the Show items and Filter Sessions…, that Go holds Back, Forward, Show Recent Places, Next Needing You, Next and Previous Session, Open Manager, Search Sessions…, Ask Switchboard…, and both Move Focus items, and that the Session menu holds none of them but still holds Message Claude and Stop Claude. Then it selects two sessions, posts presses of mouse buttons 4 and 5 to the app, and checks that they go back and forward between them. After that it runs the app's `DropSelfTest` (`SB_DROP_TEST`) in the session view, the Inbox, and a group chat. A script can't move the mouse without the Accessibility permission, so the test calls the drag-destination methods of the view that AppKit's own drag hit test picks under the message field, with file URLs on a pasteboard of its own. It drops sets of images, a text file, and a folder, with the field unfocused and focused, drags text and a link, pastes several images, and clicks Send. It checks the chips, the errors, and the copies that sbd made, and leaves `chips.png`, a picture of 20 chips, in `.build/gui-test/drops`. The shortcuts check walks the menu bar and checks that each item with a key has the key of the `AppShortcut` entry that names it, and that each menu entry in `AppShortcut` has an item. It then posts ? to the Inbox and to the overlay's sheet, and checks that the shortcuts overlay opens and closes, and that Help > Keyboard Shortcuts opens and closes it too. `AppShortcut` in `Sources/SwitchboardApp/AppShortcut.swift` lists every keyboard shortcut, and the menus, buttons, help tags, and the overlay read it. `AppShortcutTests` fails when a source file binds a key with a raw `keyboardShortcut` call or spells a shortcut glyph by hand, so a new shortcut goes into that list. CI's `gui-test` job runs every check but drops (`SB_GUI_SKIP=drops`).

`SB_ORG_FILTER=posthog,(local)` starts the app with that org filter, `SB_GROUP_FILTER=<group id>,(ungrouped)` starts it with that group filter, and `SB_ORGS=open` opens the filter's menu once `sbd` lists the sessions. None of them saves a filter. `SB_HISTORY=board,<id>,inbox` goes to each place in turn once `sbd` lists the sessions, so each one adds to the Back history. `SB_HISTORY_BACK=<n>` then goes back n times, and `SB_HISTORY_MENU=open` then opens Recent Places. A launch that sets `SB_SNAPSHOT`, `SB_TERMINAL_TEST`, `SB_DRAFT_TEST`, `SB_SHELL_TEST`, `SB_DROP_TEST`, or `SB_QUIT_FILE` runs the app in the background, and every launch in `bin/test-gui` sets one of them. The app then has no Dock icon and never becomes the active app. Its windows and sheets are fully transparent, and clicks pass through them to the windows below. A test run therefore never takes your keyboard focus or covers your windows. AppKit still lays out and draws the windows at their usual size, so the checks and the PNGs match those of a visible run, except that `pane-preedit.png` draws the marked text on row 2 instead of the cursor row. The test app's menu bar item still appears while it runs. To watch a run, for example to debug a failing check, set `SB_TEST_VISIBLE=1`: `SB_TEST_VISIBLE=1 bin/test-gui` shows the window and brings the app to the front, as a normal launch does.

`bin/measure 10 25 100` measures each count in turn. It builds `sb` and `sbd` in release mode, runs the panes in your login shell, and reports the memory of `sbd`, of the terminals, and of the stub claudes, with the median of 5 runs of `sb ls` and `sb ls --json`. sbd's live cap limits how many stubs run: `--cap N` sets it, and sbd's default applies otherwise. The stub stands in for claude, so the numbers leave out claude's own memory.

`bin/measure --running` measures the `sbd` at `SB_HOME` (`~/.sb` by default) as it runs, through the `sb` on your `PATH` or the one in `SB_BIN_DIR`. It prints the session count, the live claude processes, and the memory of five groups: `sbd`, the terminals and shared MCP servers, the live claude processes, the processes that claude started (tools and hooks), and the app. `--json` prints the same as JSON.

Both modes report physical footprint, which is the number Activity Monitor shows, and the sum of resident sizes beside it. Each claude process maps about 230 MB of its binary, and those pages are in memory once however many processes map them. A sum of resident sizes counts them once per process, so it overstates the total by about 230 MB for each live claude after the first.

`MeasureTests` in `bin/test` checks that `sb ls` answers in under 1 s with 25 sessions, and skips the timing when the load average is above the core count. `MeasureRunningTests` checks `bin/measure --running --json` on a private `sbd`.

The stub plays the hook payloads that `bin/test --claude` records in `Tests/IntegrationTests/Fixtures/claude/`. After a Claude Code update, run `bin/test --claude` and read `git diff` on that folder to see what the new version sends.

`spikes/phase0/` holds the Phase 0 tests that measured the Claude Code and GitHub behaviors this relies on.

`SwitchboardCore/Deploys.swift` reads PostHog's deploy signals: the deploy comment on PostHog/posthog PRs, the PostHog/charts state files, and the charts deploy runs' sync jobs. `SwitchboardCore/DeployWaits.swift` turns them into a deploy wait's outcome, and `GitHubPoller+Deploys.swift` makes the REST calls.
