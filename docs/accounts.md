# Accounts

Each session runs `claude` under one Claude account, a config folder such as `~/.claude` or `~/.claude-personal`. A session keeps its account until you move it, because its transcript lives in that folder. `sb account` lists the accounts that hold a login and marks the active one. `sb account use <name|folder>` makes it the account for new sessions, and so does a click on the account in the app's toolbar account menu or a choice in Settings ▸ General. Settings never offers to move existing sessions, so use the toolbar menu or `sb account move` for that. The name of `~/.claude-personal` is `personal`, and the name of `~/.claude` is `default`. The choice survives a restart of sbd. `sb account use`, `sb account move`, and the app refuse an account that has no login, as the last read of its usage found it (see `sb usage`), and the error names the command that signs it in. sbd reads the usage again before it refuses, so an account that has just signed in is accepted. An account whose read failed for another reason, such as a locked keychain, and an account that sbd has not read yet are accepted. When sessions on other accounts could move to the new one, `sb account use` in a terminal and the account menu ask whether to switch only new sessions or to move the existing ones too. `--move` and `--new-only` answer for `sb account use`, and a script that gives neither gets the new sessions only. `sb account move <name|folder>` moves them without switching, and `--dry-run` lists what would move. The account menu offers the same move to the active account when a session on another account could move to it. `--session <ref>` moves only the session it names, by id, id prefix, or name, and can repeat. A named session that stays, because its claude runs, it already runs under the account, its group runs its sessions under another account, or for any reason below, makes the command exit nonzero. `--stop` stops a named session's claude first and moves it once claude exits. It stops only a session that its running claude alone keeps from moving, and it needs `--session`. `sb stop` answers once claude exits, or after 5 s, so `sb stop <ref> && sb account move <name> --session <ref>` moves the session too.

The app shows a session's account in its header, such as "Account: personal". Clicking it, or Move to Account in a session's context menu in the session list, the Board, the Inbox, or the conversation list, lists the accounts with each one's 5-hour and weekly usage, the way the toolbar's account menu reads them. The session's account has a checkmark, and an account whose last reading found it signed out is disabled and says so. When the session's group names an account, the other accounts are disabled, the menu says "Its group, <group>, runs on <account>. Change the group's account instead.", and Show <group> on the Board opens the lane whose account menu changes it. The menu shows when sbd lists more than one account, for a session on this Mac that has started. A pick sends the same request as `sb account move <account> --session <id>`, first as a dry run, and shows sbd's reason when it refuses. An idle session moves at once. A session whose claude runs asks first ("Stop <name> and move it to <account>?") and then stops and moves it, and it restarts on the new account with its next message. A Manager conversation, the operator, and a group chat each keep their own account and move on their own. Their move always asks first, and the question names what changes: the MCP servers in the conversation's list that the new account doesn't have, the Manager folder's memory, which each account keeps separately, and claude.ai connectors such as Slack, which belong to each account's claude.ai login. `sb account move` names those servers in a "drops MCP servers" line, and `--json` lists them as `mcpDropped`. `sb get` shows a session's account on its `account:` line.

A move copies the conversation's transcript to `<account>/projects/<same folder>/<id>.jsonl`, with the conversation's own folder (its subagent transcripts and tool results) and its `file-history` folder, and then switches the session to the account. The old copy stays. An account whose `projects` folder is a symlink to the other's already holds the transcript, so nothing is copied. A move replaces an older copy of the transcript that an earlier move left, and refuses a session whose account already holds a different one. Only a session whose claude is stopped moves: a running claude, or a message on its way, keeps writing the old transcript, and a second claude that resumes the conversation forks it. Such a session stays and `sb account move` lists why. A moved session's next resume runs under the new account's settings, MCP servers, and permissions, and may write the whole conversation to the prompt cache again. The session's shell pane keeps its old `CLAUDE_CONFIG_DIR` until it restarts.

sbd also lists Codex accounts. A Codex account is a `CODEX_HOME` folder: `~/.codex` is named `codex`, and `~/.codex-work` is named `codex-work`, so the name keeps the agent and never matches a Claude account's. `sb account` shows each account's agent in a column, and `sb account --json` and `sb usage --json` give each account an `agent` key, `claude` or `codex`. A folder needs no file to count, because a Codex login kept in the keychain leaves none. A folder named like a Codex folder that holds a Claude login (`.claude.json`) is neither kind, so sbd leaves it out of `sb account`, logs why when it starts, and refuses a request that names its folder. `codexHomes` in config.json replaces discovery with its list of folders, the way `claudeConfigDirs` does for Claude accounts. An entry there may have any name, but one named like a Claude folder or holding a Claude login is refused. A name that a Claude and a Codex account share, such as `codex-work` for both `~/.claude-codex-work` and `~/.codex-work`, picks neither: name the account by its folder. `sb account add <name> --agent codex` makes `~/.codex-<name>` and prints `CODEX_HOME=~/.codex-<name> codex login`, which you run to sign in. `--agent claude` makes `~/.claude-<name>` and prints the `claude` command to run, and then `/login` inside it. The name starts with a letter or digit and takes letters, digits, `.`, `_`, and `-`, and an existing folder is refused, because it may hold a login. A new Claude folder is listed once it holds a login. With `codexHomes` or `claudeConfigDirs` set, add the new folder there too. Sessions run only on Claude accounts for now: `sb new`, `sb spawn`, the MCP `spawn` tool, `sb followup add`, `sb account use`, `sb account move`, and `sb group account` refuse a Codex account, the app's account menu doesn't let you choose one, and the New Session sheet and the group account menu don't list them. A session, follow-up, or group whose stored account folder has since become a Codex account doesn't start or move there, and sbd's own `claude -p` calls for it run under `triage.account` or the active account instead.

A session that another session starts (`sb new` or `sb followup add` inside a session) uses its parent's account, whatever is active. `--account` on `sb new` and `sb followup add` picks another. A follow-up with no parent takes the active account when it starts.

A group can name the account that its sessions run under, with `sb group account <group> <name|folder>` or the account menu in the group's lane on the Board. `sb group account <group> --clear` removes it, and `sb group account <group>` shows it. It overrides the active account and a parent's account for every new session in the group, its chat included, and sbd refuses an `--account` that names another account. A running claude keeps its account. At each launch or resume, sbd moves a stopped session whose account differs from its group's, the same way `sb account move` does, so a session that joins the group, or that ran while you set the account, moves at its next launch. When the move can't happen, because the group's account folder holds no login any more, its last usage reading found it signed out, or it already holds another transcript of the conversation, the session launches under its own account and `sb events` shows an `account-move-skipped` event with the reason. sbd tries again at the next launch. Clearing the account, removing the group, or moving a session out of it moves no session: each stays on the account it last ran under. `sb account move` and the toolbar account menu leave a session whose group names another account where it is, and list why. New sessions in a group whose account folder no longer holds a login use the account they would use without the group. sbd refuses to set an account that has no login.

`sb usage` shows each account's use of its 5-hour session limit and its weekly limits, with when each resets, as `/usage` shows them inside claude. An account whose `.claude.json` names its plan Ultra has no 5-hour limit, so `sb usage`, the toolbar, and the account menu show only its weekly limits, as in `max · wk 8%`. The app's toolbar has an account button whose tooltip shows the active account's name, its session percent, and its highest weekly percent, as in `automation · 5h 66% · wk 82%`. The button turns the needs-you color when a limit is spent, or the read failed and there is no earlier reading. A click opens the account menu, which reads every account again as it opens, and lists every account with its number of sessions, its limits, and when each resets, and checks the active one. A click on another account makes it the account for new sessions. An account that is not signed in shows the command that signs it in, and the menu does not let you choose it. sbd reads the numbers from the endpoint that claude's `/usage` reads, which reports use and runs no model, with the account's own login from the keychain or its `.credentials.json`. A token that is about to expire is refreshed through `claude mcp get`. sbd reads every account every 5 minutes, and `sb usage` reads them again first. An account whose read fails shows why, such as an account that is not signed in, which `sb usage --json` also marks with `"signedOut": true`. `sb autocontinue` doesn't continue a session whose account has a spent limit. A Codex account's limits come from the last `token_count` event of the most recently started thread in its newest day folder of rollouts, `$CODEX_HOME/sessions/YYYY/MM/DD`. While two Codex threads overlap, they can be older than the account's last Codex turn. A thread writes its rollout in the folder of the day it started, so sbd doesn't see the readings of a thread that started on an earlier day. Right after midnight, a new Codex thread that hasn't finished a turn hides the previous day's limits until it does. `sb usage` shows when Codex reported them, `--json` marks them `"source": "rollout"`, and their `checked` is that time. Until a rollout has them, `sb usage` says "no Codex limits seen yet; they appear after the account's next Codex turn". sbd runs `codex login status` (the `codex` setting names the program) to tell whether a Codex account is signed in, and a signed-out account's error names the `codex login` command.

`sb usage headless` sums the tokens of the `claude -p` calls that sbd makes for itself, for each day and kind: the turn summaries (`triage`), the merge briefs (`mergeBrief`), quick asks (`quickAsk`), plan status updates (`planUpdate`), the labels of the Manager's skills (`skillLabel`), and the names of new sessions (`sessionName`). Each line shows the calls, the calls that gave no usable answer, the input, output, cache read, and cache write tokens, and the models that claude reported. `--since` sets the window (default `7d`), and `--json` prints the report. sbd stores one row per call in its database, which a removed session leaves in place, so the counts include the calls of sessions that are gone. A call that timed out or failed before claude answered has no token counts. The `triage` and `mergeBrief` events also record the call's `usage` and `model`.
