# Sessions

## The window

In the app, press ⌘N to start a session. Pick a repository from the list of the ones you have used, most recent first: type to filter the list, paste a path, or choose Add repository… to add one from a folder. A worktree or a subfolder adds its repository's main checkout. Turn on Create a worktree to get a new branch in `~/dev/worktrees/<repo>/<branch>`, and give the session a first prompt. Turn on Start in plan mode to start claude in plan mode, so it writes a plan and waits for your approval before it edits a file. The sheet's Group picks a group for the session to join. The repository then defaults to the one that most of the group's sessions run in, until you pick one, and a group that names an account fixes the session's account. `sb repo` prints the same list, and `sb new <folder>` starts a session in any folder, including one outside git. The sidebar sorts sessions into Needs you, Ready to merge, Claude can continue, Ready for review, Waiting, Working, Done, and Stale, with a reason for each. When the sidebar's sessions are in more than one repo, each row shows its repo in front of the reason, as in `switchboard · Waiting on review`. The repo is the main checkout of the git repo that holds the session's folder, or else the session's PR's repo. For a worktree that `sb new` made, that checkout is the folder it made the worktree from, and for any other worktree, such as one that Supacode made, it is the checkout that `git worktree list` names first. A session in a folder outside git with no PR shows no repo and doesn't count as a repo. `sb ls --json` shows the checkout as `checkout`. Two repos with the same name, such as a fork and the original, show `owner/name`. The Manager's row never shows a repo. The Inbox's rows and the Board's Repo lanes show the same repo names. Waiting holds the sessions that wait on a wait you set, and the sessions whose turn has ended while subagents run, such as the reviewers of `/review-code`, when the last reply asks nothing and offers nothing. Ready for review holds the sessions that would otherwise be in Waiting and whose open PR is out of draft and needs a review that the base branch's rules ask for, including each session whose PR waits only on a requested reviewer, as after Request review on the review card (see [The Inbox](inbox.md)). Select a session to get its Claude terminal and its shell side by side. The × on the shell's label, Close Shell in the Session menu, and `exit` or Ctrl-D in the shell all end the shell and remove its pane. The shell stays closed when you switch sessions and when the app or `sbd` restarts, until Open Shell on the Claude terminal's label, the Session menu, `sb shell <session> --open`, or `sb attach <session> --shell` starts a new one. Closing the shell leaves claude running. A new Manager conversation, group chat, or operator shows Claude's terminal alone, because sbd starts it with its shell closed, and Open Shell starts one. ⌘W closes the Switchboard window, as in other Mac apps, and leaves both terminals running. With no session selected, the Inbox shows the triage list (see [The Inbox](inbox.md)), and ⌘J moves to the next item. The Inbox, Board, Issues, and Loops buttons in the toolbar, or ⌘1, ⌘2, ⌘3, and ⌘4, deselect the session and show the Inbox, the Board, the Issues view (see [Issues](follow-ups-and-issues.md#issues)), or the Loops view, which lists every schedule and the operator's Background Activity (see [The Manager](manager.md)). A permission prompt or an `AskUserQuestion` question shows there, and above the session's terminals, as a card that you answer without opening the session. With a session selected, ⌘J jumps to the next session that needs you. ⇧⌘] and ⇧⌘[ (Go > Next Session and Previous Session) step to the next or previous row of the sidebar, item of the Inbox, or card of the Board, whichever shows, around the ends, and skip the rows of a collapsed section. ⌘L (Move Focus to List) puts keyboard focus on that list from anywhere, including a terminal. ⌘T (Move Focus to Terminal) puts it in the Claude terminal of the selected session, the current Inbox item, or the Board's ringed card. In the sidebar and the Inbox list, ↑ and ↓ move and stop at the ends, and Return goes into the Claude terminal. On the Board, the arrow keys move a ring from card to card, and Return opens the card as a click does. ⌘K (Go > Search Sessions…) opens a search panel that matches what you type against each session's name, repo, branch, PR number and title, issue number, group, reason, and notes, best match first and then the most recent activity. ↑ and ↓ move in its list, Return selects the session in the sidebar, and Esc closes the panel. The Search Sessions field at the top of the sidebar matches the same way and filters the sidebar's work sessions in place, in their usual order. A child whose parent doesn't match shows at the top level. The field leaves the Conversations section, the Inbox, and the Board as they are. ⇧⌘K (Go > Ask Switchboard…) opens a panel that takes one question about Switchboard, such as "what's waiting on me?", and shows the answer in the panel. It answers as `sb ask` does (see [The Manager](manager.md)), so it can't start a session or change anything. Return asks, and Return again asks the edited question. Closing the panel discards the answer and ends an ask that is still running. Continue as Chat starts a Manager conversation whose first prompt carries the question and the answer. The Back and Forward arrows at the left of the toolbar, ⌘[ and ⌘] (Go > Back and Forward), and mouse buttons 4 and 5 go back and forward through the places you went, as in a browser: each session you select from the sidebar, the Inbox, the Board, search, a link, the menu bar, or a notification, each switch between the Inbox and the Board, and each switch of the Inbox between an item's overview and its terminal. A three-finger swipe does the same when System Settings > Trackpad sets Swipe between pages to three fingers. Going somewhere new after going back drops the places ahead, a repeat of the current place adds nothing, and the history keeps the last 50 places while the app runs. Back and Forward skip a session that was removed or that the org filter hides, and they turn gray when there is nowhere to go. The clock button next to them, or ⌘Y (Go > Show Recent Places), lists the last 10 places, newest first, to jump to. A focused terminal keeps every key except the menu bar's ⌘ shortcuts, so ⌘L is the way out of it. Full Keyboard Access (System Settings > Keyboard) reaches the other controls with Tab. The menu bar shows how many sessions need you, and a notification fires when one starts to.

## Filters

The filter in the toolbar shows the sessions of some GitHub orgs or some groups only. It reads "All Sessions" until you narrow it. A click, or ⇧⌘O (View > Filter Sessions…), lists each org that has sessions and each group, with its count, how many need you, and a checkbox. Local holds the sessions whose repo has no GitHub `origin` remote, and the sessions outside git. Ungrouped holds the work sessions in no group. A session shows when both the org filter and the group filter allow it, and an org's or group's count is how many sessions checking it would add. The filter applies to the sidebar, the Inbox and its count, the Board in both lane modes, the Dock badge, the menu bar item, notifications, ⌘J, session search, Merge All, and Send All. A group's Board lane hides when the group filter leaves the group out or the org filter hides every member, and a group suggestion shows only when the filter shows all its sessions. While a filter is on, the toolbar names it in the accent color, such as "PostHog, Local", "Infra +2", or "PostHog · Infra", and a bar under the sidebar says how many sessions it hides and how many of those need you, with Show All, which clears both filters. When the filter hides every work session, the Board and the sidebar say so, with Show All. The filter only hides: `sbd`, the Manager, and every session keep running. The Manager always shows. A group chat shows when the group filter allows its group, because its items are about that group's sessions. A chat whose group was deleted always shows. A hidden session that starts to need you sends no notification. Delete All in Done deletes only sessions that the filter shows. When the app opens a session that the filter hides, such as a new session or a notification's session, it adds that session's org and group to the filter. Moving a session to a group, New Group, and accepting a group suggestion add the group to a group filter that is on. A session whose folder `sbd` has not read yet shows under every org filter. The installed app remembers both filters across launches. A deleted group leaves the group filter. `sbd` reads the owner from the `origin` remote of the session's main checkout, and `sb ls --json` carries it as `repository`, with `repositoryRead: true` once `sbd` has read it. `sb ls --org posthog,haacked` lists the sessions in those orgs, and `--local` adds the Local ones. `sb ls --group Infra,Search` lists the sessions and the group chats of those groups, by name or id, and `--ungrouped` adds the sessions in no group.

## The Board

The Board is a Kanban board. It has a lane per repo and a column for each step of a session's task: In progress (Claude is in a turn, or the session has not started), Waiting (work stopped on something other than a review, such as a question for you, CI, another session, a timer, or a background job), In review (the PR is open and waits on a review), Approved (approved, CI green, and no conflict), and Merging (in Trunk's queue or GitHub's merge queue). The Repo and Group control above the lanes switches to a lane per group, which shows each group's description, chat, and plan rows beside its sessions. A card shows its column and how long it has been there, such as "In review 5h", and one line: what Claude does now in In progress, what the card waits on in Waiting, the reviewers it waits on in In review ("waits on alice, CI running"), who approved it in Approved, and the queue's state and text in Merging ("Trunk testing"). A Waiting card has a badge that says who holds it: you, a machine, or another session. A card whose PR moved back shows why, such as "back from Approved: new commits", until the PR reaches that column again. Needs you is not a column: a card whose session needs you keeps its column and gets an orange edge, and you answer it in the Inbox. A dot in the state's color marks a card whose session has an Inbox item. Each column lists the card that has been in it longest first. From 4 hours in review, an In review card has a Nudge button that copies a message for its reviewers, such as "@PostHog/team-flags could you take a look at #1234 (Cache flag reads)? It has waited for review for 5 hours." and the PR's link. An Approved card whose session is Ready to merge has a Merge or Enqueue button. A conflicted card has a button that asks the session to merge origin/main in, resolve the conflicts, run the tests, and push. Done sessions and merged PRs collapse into one "Done and merged" line under the lanes. `sb get` prints the session's board column as `column:  In review 5h; waits on alice, CI running`, followed by any "back from Approved: new commits" note, and `sb ls --json` and `sb get --json` have it as `board`, with `column` (`in_progress`, `waiting`, `in_review`, `approved`, `merging`, or `done`), `since`, `line`, `holder` (`you`, `machine`, or `session` on a Waiting card), `reviewers`, and `back` (`from`, `reason`, and `at`), on every work session. The Manager, group chats, and docket rows have none.

## The session's issue

Each work session shows the GitHub issue it works on, as `#174`, in its sidebar row, its Board card, its Inbox row, and its header. `sbd` finds the issue in a closing keyword of the session's PR body, such as `Fixes #174`, `Closes owner/name#174`, or `Resolves` and an issue URL (any of GitHub's nine closing keywords, outside HTML comments and code fences). Without one, it takes a number at the start of the branch's last part, followed by `-` and a letter, as in `haacked/174-issue-in-tile`, unless the number is the PR's own. `sb issue <session> <ref>` sets the issue by hand and replaces both, and `sb issue <session> --clear` removes it. An issue in another repo than the PR's shows as `owner/name#174`. A tile shows the first issue and how many more there are, such as `#174 +1`, and its tooltip lists them all with where each came from. Before the session has a PR, an issue from the branch shows with no link, because `sbd` doesn't yet know the repo. `sb get` prints an `issue:` line for each, and `sb ls --json` and `sb get --json` have them as `issues`, with `repo`, `number`, `via` (`set`, `body`, or `branch`), and `url`. The issue's title and state don't show.

## Deleting sessions

The trash button in the session header removes the session: it stops claude and closes both terminals, and the folder and the conversation's transcript stay. Its dialog also offers to delete the session's worktree, and, with the worktree, its local branch. Both are off by default, and neither is offered for a session that sbd made no worktree for. Deleting the worktree, which `sb rm --worktree` does too, refuses when the worktree has uncommitted files, files that git status skips through assume-unchanged or skip-worktree, or commits that are on no remote branch (unless the session's PR is merged). It deletes the worktree's ignored files. Before it deletes the worktree, sbd closes both terminals, waits for claude and the other processes the way `sb cleanup` does, and checks the worktree again, so it also refuses a file that claude writes as it stops. Deleting the branch, which `sb rm --worktree --delete-branch` does too, refuses unless the session's PR is merged and the branch has no commit after it. A refusal changes nothing and shows the error. The branch is checked again after the worktree is removed, and it is kept, with an error, when it has moved off the merged PR's head, is gone, or is checked out in another worktree. The worktree and the session are removed in that case, because the session's folder is missing. A trash icon on each Done card and sidebar row, and the Done section's context menu, ask for all of it at once, after a confirmation that names the session, the worktree, the local branch, and the remote branch. It is never on the Manager. The icon hands the session to sbd's removal job and returns at once: the session leaves the sidebar, the Inbox, and the Board, and a "Removing 1 session…" row at the bottom of the sidebar shows while the job works. The job waits 5 s before it starts a session, and for those 5 s the row has an Undo button. Undo brings back every session whose delete hasn't started, with nothing stopped, and they return to the lists unselected. A session that started in the meantime stays deleted, and the error banner says so. Undo works for a delete from `sb rm --done` too, while the session is in the row. A session that fails a check comes back to the Inbox as "Delete failed" with the reason, a Retry button that queues it again, and a Keep button that cancels the delete and keeps the session. `sb rm --keep <session>` does what Keep does, for a Manager or a script. sbd drops the failed delete on its own when the session gets a prompt, starts, resumes, is unpaused, or is marked not done, as long as its folder is still in place, not in the trash, and git still lists the worktree. A remote-host session keeps its failed delete. A user who still wants the session gone deletes it again. A branch that the job had to keep after it removed the session shows in the Removing row's popover, with Dismiss. It leaves the branch alone when the session's PR is not merged, and `sb rm --worktree --delete-branch --delete-remote-branch` does the same work: the remote branch goes only when it is at the merged PR's head, and stays, with an error, when it is not. A worktree that `git worktree lock` locks is refused before anything stops, unless Supacode locked it (the lock reason is JSON whose `owner` is `supacode`). sbd removes such a worktree, when it passes every other check, with `supacode worktree delete --worktree <id> --background`, where the id is the worktree's path with a trailing slash, percent-encoded, and then checks that git no longer lists it. It never unlocks a worktree or forces git. With Supacode's lock, the local branch goes only when `origin/main` contains its tip, so a squash-merged branch stays. A missing or failing `supacode` refuses the removal with its reason. The `supacode` key in `config.json` names the program, `supacode` on PATH by default. `sb cleanup` handles Supacode's lock the same way and keeps the session. A session whose folder is gone has only its own worktree record removed from git, after the same locked and unpushed-commit checks on the worktree's HEAD, and its branch passes the same checks. A branch that is already gone is not an error.

The Done heading in the sidebar and the Board's "Done and merged" line have a Delete All button. Both act on every Done session except the Manager, across every group, and the button is off when there is none. sbd first runs the trash icon's checks on each session, and a sheet lists the sessions it will delete, with each one's PR and whether its worktree, local branch, and remote branch go, and the sessions it will skip with the check that failed. Nothing is deleted until you confirm. Confirming closes the sheet and hands every session to sbd's removal job, as the trash icon does, and the sessions leave the lists at once. The job deletes them one at a time and checks each again first. A session that sbd skips when you confirm stays in Done, and the error banner names it with the reason. A session that fails a check later comes back to the Inbox with Retry and Keep. For 5 s after you confirm, the Removing row's Undo brings the sessions back, as it does for the trash icon. `sb rm --done --worktree` does the same from a terminal: it lists the plan and asks first, needs `--yes` without a terminal or inside Claude Code, and with `--json` and without `--yes` prints the plan and deletes nothing. Once you confirm, it hands the sessions to the same removal job and waits until the job has deleted each one or failed it, so it takes 5 s longer than the deletes themselves. A session that the app's Undo brings back in those 5 s is reported as skipped. It then prints what it removed, what it skipped with the reason, and each session whose branch or remote branch stayed. A session that fails in the job goes back to Done. A kept branch that `sb` prints no longer shows in the Removing row's popover. With `--no-wait` it prints the sessions it queued and the ones it skipped, and returns while the job runs, so a later failure shows in the Inbox. Without `--worktree` it removes only the sessions, and `--delete-remote-branch` also deletes each merged branch on its remote.

⌘-click or ⇧-click rows in the sidebar to select several sessions in any state. The detail pane then lists them with **Delete N Sessions…**, which the selected rows' context menu and ⌘⌫ in the sidebar also offer. N counts the selected sessions it can delete, including selected rows in collapsed sections, and it opens the same sheet as Delete All, which names every session it deletes or keeps. A session whose claude is working says that claude stops, and the Manager and follow-ups that haven't started stay. Confirming hands the sessions to the removal job, and they leave the lists.

## The session menu

Right-click an Inbox item, a sidebar row, a Board card, or a conversation for the same session menu everywhere. It lists Highlight, Snooze, Copy Link, Pause, Start Now for a queued session, Stop Claude while claude runs, and the row's own items, such as Move to Group on the Board and Pin on a conversation. A divider then separates the items that delete: Clean Up when the cleanup is ready, and last, Delete…, which asks for the same confirmation as the trash icon. Delete… is offered for a work session in any state, so an Inbox item can be deleted from where it is, and never for the Manager, a chat, or a follow-up that hasn't started. A session that isn't Done goes to the removal job the way Delete N Sessions… sends it, so its claude stops, and the job refuses a worktree with uncommitted files or unpushed commits as described above. On a row that belongs to a multi-selection, the menu offers Delete N Sessions… in place of Delete….

## Cleaning up merged work

When a session's PR merges and its worktree has no uncommitted file, the poller also runs the cleanup checks. The session's reason then reads "#N merged; ready for `sb cleanup`", and `sb get --json` shows `cleanup` as `ready`, or as `blocked` with the check that failed. sbd never removes a worktree by itself. `sb cleanup <session>` checks again, closes the shell terminal, stops claude and waits up to 5 s for it to exit, closes the Claude terminal, and waits up to 5 s more until every process that ran below either terminal has exited and no process has its working folder, its program, or an open file in the worktree. It then checks once more, and removes the worktree and the local branch. A claude that is still running after the first 5 s refuses the cleanup and keeps its terminal open, so `sb cleanup` can run again once it exits. A process that holds a folder in the worktree open only as a folder, as a file watcher such as Supacode does, doesn't count, because macOS opens a folder only for reading. Neither does the working folder of the background ssh process that `git push` leaves for ControlPersist, named `ssh: <socket> [mux]`, because ssh never touches that folder after it starts. A process that still runs or still uses the folder after the second wait, such as a background job, a `nohup` command from the shell terminal, or an editor with a file open, refuses the cleanup, and the error names its pid, its command, and why it blocks: `started by the session`, or `cwd`, `program`, or `open file` followed by the path. sbd sends those processes no signal. A retry no longer finds a background job or a `nohup` command below a closed terminal, so it treats one that meets the rules below as a leftover. A leftover is different: a process that still uses the worktree, whose parent is pid 1, so no process waits on it, that started after the session did, and whose environment holds the session's `SB_SESSION_ID`, so the session started it. A dev watcher that a Bash command started, such as `hogli watch`, is one. sbd's tmux server never is, and neither is a program that ships with macOS, such as `/bin/sh`, because macOS hides its environment. When every recorded process has exited and only leftovers still use the folder, sbd sends them SIGTERM, waits up to 5 s, sends SIGKILL to any that still run, and goes on. This applies only to sessions on this Mac. The session stays in Done with "#N merged; worktree and branch removed". It refuses, and changes nothing, unless the PR merged the session's branch, sbd made the worktree, no other session runs in it, git doesn't lock it, no turn runs, the branch's tip is the merged PR's head, and the folder has no uncommitted file, no file that git status skips through assume-unchanged or skip-worktree, and no ignored file except build output such as `node_modules`, `.venv`, `target`, `__pycache__`, `dist`, `build`, and the caches of ruff, pytest, mypy, flox, trunk, and husky, and a top-level `.notes/` folder. `cleanupDeletes` in `config.json` adds more ignored files and folders that cleanup may delete, such as `[".env"]`. A closed PR is refused, because its branch may hold the only copy of the work. In the app, a ready session shows a Clean Up button (a sparkles icon) on its Done card, its sidebar row, and its session header, and in its sidebar context menu. Each one asks first, in a confirmation that names the worktree and the branch, and then runs the same `cleanup`. A refusal shows sbd's message in the error banner. A blocked session shows the failed check on its card, its row, and its header. After cleanup, the session's reason says what cleanup removed.

## Messages

A message that `sbd` accepted survives a restart of `sbd`, even a crash. `sbd` refuses a message whose `sent` event it can't store. It records `pasting` just before each paste starts and `delivered` once it succeeds, and it starts no paste whose `pasting` it can't store, trying again a second later. A message whose paste had not started goes out again after the restart, without waiting for the session's next hook. A message whose paste started without a `delivered` may or may not have reached Claude, so `sbd` never pastes it again on its own. It looks in the session's transcript for a user message with that text that Claude wrote after the paste started. When it finds one, it records `delivered`. Otherwise it records `delivery_unknown` and leaves the message to you. `sb events <session>` shows these events.

A session's terminal view has no message field, because you type to Claude in its terminal. Session > Message Claude (⇧⌘E), or the Message button over the terminal, shows the field there to attach images. Esc in the empty field or a sent message hides it again, and a field that holds a draft stays. A message can carry images. Drop png, jpg, gif, webp, or heic files or a screenshot's thumbnail on the message field in the Inbox or a session's view, or on a session's Claude terminal, or paste screenshots from the clipboard, and each shows as a chip with a remove button, in the order of the drop. A drop or paste can hold several images, and it adds them to the chips already there, whether or not you are typing in the field. Many chips scroll sideways in one row. `sb send <session> --image <path>` does the same, once per image. The app or `sb` reads each file, and refuses a file that isn't an image by its content, a folder, a symlink, or a file over 20 MB. A message carries at most 20 images and 100 MB of them. The app attaches the images of a drop that fit, and names each file it left out and why. `sb` and sbd refuse a message over a limit. sbd keeps a copy in `~/.sb/sessions/<id>/attachments`, converts HEIC to PNG, and sends your text and then the copies' paths, which Claude Code attaches as images. A stopped session starts and gets the message as a paste, because Claude Code doesn't attach the images of a first prompt. `sb rm` deletes the copies with the session. The files you dropped stay where they are. A screenshot dropped from its thumbnail that the app leaves out goes to the Trash, so it isn't lost.

What you type in a message field stays there when you switch to another session or view and come back, until you send it or press Esc twice within a second. The first Esc shows "Press Esc again to clear" in the field. A session's field keeps its own draft, and a group chat's draft belongs to the group. The app saves drafts, images included, in `~/.sb/drafts`, so they survive a relaunch, and drops a draft when its session is removed. Drafts never reach `sbd` or the event log.

## Permission cards and questions

A card waits until you answer it from `sb` or the app, or answer Claude Code's own dialog in the terminal. When Claude Code stops waiting on the hook, as after a day or when `sbd` restarts, a Bash, Edit, Write, or Read prompt or a question keeps its card while the dialog shows, and `sb cards` marks it `hook closed`. Its answer is typed into the terminal: `sb allow` picks Yes, `sb deny` presses Escape and sends the message after it, and `sb answer` presses Escape and sends the answers as a message. `sb deny` with a message lets Claude read it and go on. Without one, the turn stops, as No does in the terminal. `sb answer` takes one answer per question, in order. A multi-select answer separates its labels with commas, and text that names no option is a typed answer. A question that stays open for `idleStopSeconds` while no terminal shows its session is deferred: Claude ends its turn, `sbd` stops `claude` on its normal schedule, and your answer resumes the session. `sb cards` prints the whole tool call that `sb allow` approves. `sb allow`, `deny`, and `answer` refuse to run when `CLAUDECODE` is set, as it is for every command that Claude runs. That keeps a session that follows injected instructions from approving tool calls with `sb`, though a process that clears the variable gets past the check.

A permission card from a session in manual or accept edits mode also offers "Approve and enable auto mode", in the Inbox and above the session's terminals, and `sb cards` marks it `--auto offered`. It allows the call and switches the session to auto mode, where Claude's classifier decides further permissions instead of opening another card. `sb allow --auto <session>` does the same. sbd answers the held hook with Claude Code's `setMode` permission update, so the switch needs a live hook: a card whose hook closed, or a card from auto mode, refuses `--auto` and shows no button. A plain Allow never changes the mode. `sb get` shows the session's mode on its `mode:` line, `sb get --json` and `sb ls --json` carry `permissionMode` (`default` is manual mode), and the session view shows it next to the claude state. sbd reads the mode from the last hook, so a switch with shift+tab in the terminal shows at the next hook.

## Importing sessions

To bring in Claude sessions that you started elsewhere, press ⇧⌘I in the app or run `sb import`. It lists the sessions that run in a linked git worktree, grouped by repo, from every Claude account: `~/.claude` and each `~/.claude-*` folder that holds a `.claude.json`. `sb import --all` lists every session. `--repo <name>` lists only the sessions of the repo with that name (the folder name of its main checkout), alone or with `--all`, and fails when no session to import belongs to it. The sheet has a Repo picker for the same filter. Switchboard never stops a claude that runs elsewhere, so exit claude in its terminal, or stop a background job with `claude stop <id>`, and then import the session:

```
sb import                    # sessions in worktrees; ● marks one that a claude runs now
sb import --all
sb import --repo switchboard  # one repo; add --all for its sessions outside a worktree
sb import 26275b06 6d2c57eb  # by Claude session id, id prefix, or name
```

`sbd` remembers each session it lists for a day, so a session still shows after you exit its claude. An imported session keeps its folder and its conversation. Opening it or sending it a message resumes the conversation under the account it came from.
