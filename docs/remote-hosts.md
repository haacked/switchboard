# sb on a remote host

A session on a remote host runs `sb` as a session on this Mac does. Connecting writes `~/.sb/bin/sb` on the host, a script that runs `~/.sb/bin/sb-shim cli`, and a remote session's `claude.sh` puts `~/.sb/bin` first on `PATH`, so claude and its tools find it. The shell pane's login shell sets its own `PATH`, so type `~/.sb/bin/sb` there. The host's `sb` sends its arguments, its folder, `SB_SESSION_ID`, and `CLAUDECODE` over the host's link. sbd runs this Mac's `sb` with them as a client of the host's socket and returns its output and exit status. The output arrives when the command ends, so `sb events --follow` and `sb watch` print only at the end. The host's `sb` reads stdin only for `sb summary set`. With the link down, it exits 1 at once with "can't reach Switchboard on the Mac". A remote session also gets the triage nudge that tells claude to use `sb summary set`.

Every request on a host's socket, from that `sb` or from any other process on the host, reads and acts only on that host's sessions. An id, an id prefix, or a name of a session elsewhere fails with "that session is not on <host>", and `sb ls` and `sb events` list only the host's sessions. `sb new` and `sb spawn` from the host start sessions on the host, and `--host local` or another host fails. A relative folder of `sb new`, or a `--repo` of `sb spawn` that starts with `.`, is joined to the folder that the host's `sb` ran in, and a `~` stays for the host to resolve. The host's socket refuses `rm`, `cleanup`, and `rm --done`, `send --group` and `send --pending`, groups (except `sb group show` of the group of a session on that host), chats, and the Manager, and every command that acts on this Mac, on GitHub with this Mac's login, or on every session, such as `merge`, `review`, `ack`, `triage`, `choose`, `decide`, `import`, `account`, `usage`, `mcp`, `host`, `live`, `poll`, `repo`, `followup`, `plan`, `issues`, `docket`, and `draft`. Run those on this Mac. `sb attach`, `sb hook`, `sb mcp-server`, and `sb service` refuse with "sb <command> doesn't run through <host>'s sb".

This Mac's GitHub login reads GitHub for a session on a remote host only in a repo that the host's `repos` name, compared without case. That covers the PR of the session's branch, whichever remote names its repo, the PR that the session's transcript links, the PRs that its waits name, and each PR that a `Depends on` line of its PR names. sbd reads nothing in any other repo for that session: the session shows no PR from it, gets no dependency in it, and no wait on it resolves. A deploy wait that names a service also reads `PostHog/charts`, so a host sets one only when its `repos` name that repo. A host without `repos` gets no PR for its sessions. Without a PR, `sb cleanup` refuses the session and `sb rm --done --worktree` keeps its branch. To read the repo again, add it to the host's `repos` and restart sbd.

sbd runs that `sb` under `/usr/bin/sandbox-exec` with a profile that denies by default and allows only the exec of `sb`, reads of `sb`'s folder, and a connect to the host's socket. Whatever its arguments say, it can't read or write a file of this Mac, run another program, or reach sbd's own socket or another host's. Its environment holds only the variables that sbd sets. sbd refuses the request when it can't apply the sandbox, and never runs `sb` without it. A host runs at most 8 such commands at once. sbd stops one after 600 s, when the host's `sb` closes its connection, or when its stdout or stderr passes 16 MiB, and it then exits 1 with the reason on stderr.
