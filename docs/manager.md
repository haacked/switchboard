# The Manager

`sb manager` opens a Manager conversation, an interactive Claude session in `~/.sb/manager` that manages the others through `sb`. You can have several. `sb manager new [--name N] [<text>]` starts one, with the text as its first prompt. Without `--name`, the first line of its first prompt names it, cut to 40 characters. `sb manager ls` lists them, newest activity first. `sb manager <conv> [<text>]` opens one by id or name, or sends it a message, and `sb manager <conv> --log` shows its last messages, as `sb chat` does for a group. A bare `sb manager` opens the most recent conversation, and starts one named "Manager" the first time. Every conversation shares the folder and its CLAUDE.md, and each resumes its own Claude conversation. The app lists the conversations in the sidebar's Conversations section, with a + button that starts one, as File > New Conversation (⌥⌘N) does. Pinned conversations come first, then the others, each newest activity first. A row shows the conversation's name, the time of its last message, the first line of Claude's last reply, a blue dot while it has unread replies, an orange mark while it waits on you, and a progress mark during a turn. The pin button, or Pin in the row's menu, keeps a conversation at the top. `sb manager pin <conv>` and `sb manager unpin <conv>` do the same, and `sb manager ls` marks pinned and archived conversations. A conversation that is not pinned, has no unread reply, doesn't wait on you, and has had no activity for 3 days moves to the closed Archive group at the end of the section. A new message brings it back. Search Sessions (⌘K) finds an archived conversation by name. Selecting one shows its session, where you send it messages. The toolbar star (⇧⌘M, or Session > Open Manager) opens the most recent conversation. The star turns orange while a conversation waits on you with a permission prompt, a question, a folder trust dialog, or a group message to send, and turns blue while a conversation has unread replies. A permission prompt, a question, or a folder trust dialog that stops a conversation shows in the Inbox as "Manager" or "Manager: <name>" and counts like a work session's item. Its replies stay out of the Inbox. The sessions a conversation started are top level in the sidebar. A conversation reads the plan, starts sessions with briefs in new worktrees, waits on them, tests their branches together, and merges PRs and cleans up when you say so.

End Conversation… in a conversation's header removes the conversation and opens a new one in its place. A conversation that runs for days re-reads its whole context on every turn, while what it needs to keep already lives in memory, notes, the waits it handed to the Operator, and schedules. The confirmation names the conversation and lists each of its own waits, its pause condition, and its schedules, which the end drops. It also says how many waits the Operator keeps following and how many open requests close. `sb manager end <conv>` ends a conversation from a terminal, and `--new [--name N]` also starts one in its place. The new conversation keeps the ended one's account, MCP servers, and pin, and without `--name` its first prompt names it. The chat log leaves the app, but the transcript stays on disk: `sb manager end` prints its path, and `claude --resume <id>` in `~/.sb/manager`, under the ended conversation's account (`CLAUDE_CONFIG_DIR`), reopens it, where `--json` gives the id as `claudeSessionId`. Waits handed to the Operator stay with it and still resolve. The end refuses while the conversation has waits, a pause condition, or schedules of its own that the command doesn't name: the refusal lists each one with its id and the command to run, `sb manager end <conv> --drop <id> --drop <id>`. It also refuses while a message is on its way to the conversation, while a turn or a background job runs, and while the conversation has open to-dos. Only you end a conversation: `sb manager end` refuses inside Claude Code, from any session's pane, and from a window that a session opened in sbd's tmux server, and no MCP tool ends one. `sb rm <conv>` refuses a conversation while a message is on its way to it, or while it has waits, a pause condition, or schedules of its own, which it points to `sb manager end --drop` for.

A conversation's status strip suggests ending it in a second row with End Conversation… and a dismiss button. The suggestion shows when the conversation started at least one session, every session it started is Done or gone, and it has no waits, pause condition, or schedules of its own, or when its context reached `conversationHintTokens` (see [Settings](settings.md)). No suggestion shows during a turn or a background job, while a message is on its way, or while the conversation waits on you. A dismissed suggestion returns when another session that the conversation started is done, or when the context passes the next multiple of the threshold. `sb manager hint <conv>` prints the suggestion, `--dismiss` dismisses it, and `sb manager ls` marks a conversation with one as `suggest ending`. `sb manager ls --json` and `sb get --json` give the conversation's context size as `contextTokens` and the suggestion as `endHint`. sbd reads the context size from the transcript after each turn.

`sb ask <question>` answers a one-off question about Switchboard without starting a conversation. sbd hands `claude -p` a snapshot of the sessions by state, the Inbox, the accounts, and the groups, and runs it with no tools, no MCP servers, and no settings, so the answer can't start a session, send a message, or change anything. It runs under the active account. `--json` prints the answer and the model. Ctrl-C ends the run. config.json's `quickAsk` sets the `model` (default `sonnet`) and `timeoutSeconds` (default 90, at most 300). The app's Ask Switchboard panel (⇧⌘K) sends the same request.

The operator is one background Manager session, named "Operator", that follows through on the work that conversations hand it, so the conversations don't wake for it. sbd creates it the first time something needs it. It runs in `~/.sb/manager`, so it shares the conversations' CLAUDE.md and auto-memory, and it resumes its own Claude conversation. At every launch sbd appends its role to the system prompt in place of the triage prompt, and starts claude with `--no-chrome`, because nobody sees its chat. It loads only the `switchboard` MCP server, and `sb manager mcp Operator …` changes its servers as it does a conversation's. `sb operator` opens it, creating it the first time, `sb operator <text>` sends it a message, and `sb operator --log` shows its last messages. It never appears among the conversations: `sb manager ls`, a bare `sb manager`, `sb manager <conv>`, the Manager sidebar section, and the toolbar star all leave it out, and a new conversation's start digest does not list it. When its own conversation starts, it gets the start digest of every session other than the conversations. The app doesn't show a sidebar row for it. The Loops view's Background Activity section lists its work, newest first: its reports, with "Asked: " in front of a question, and the merges and removals that its waits' actions made. Each row links to the session that it is about while that session exists. The section's Transcript button opens the operator's transcript. On macOS 15 and later, holding ⌥ in the Session menu turns Open Manager into Open Operator Transcript. `sb ls` and `sb ls --brief` leave the operator out, and `sb ls --json` keeps its row. The operator moves to Needs you only in three cases. A permission prompt, a question, or a folder trust dialog stops it. A `notify` wait outcome waits for you. Or it holds a question or an overdue wait, because no conversation exists to show it. Otherwise it is Working during a turn and Waiting the rest of the time. `sb done Operator` is refused, because sbd skips a done session's waits, and `sb rm Operator` is refused while it has an open wait, which `sb wait Operator --clear` clears, or an open report that needs you, which you answer or acknowledge first. After `sb rm Operator`, the next `sb operator` creates a new operator. It queues for the live cap and stops when idle, as a conversation does. A wait that a conversation's Claude sets on the conversation, with `sb wait`, the `set_wait` tool, or the `spawn` tool's `wait`, goes to the operator when it resumes and reads nothing of the conversation: a `session`, `date`, or resuming `manual` wait, or a PR wait whose PR names its repository (`owner/name#N` or a PR URL). sbd records the wait on the operator with `handedFrom`, the conversation's id and name, and records its `wait` event on the operator with `from`. The answer is the operator's summary, and `sb wait` prints "the operator follows this through". When the wait ends, only the operator gets the message, such as `Switchboard: kid to reach Done: it did. For Manager conversation "Plan the cache fix". Your note: remove its worktree.` These waits stay on the conversation: one that you type in a terminal, one with `--here` (`here: true` on `set_wait`), `--then notify`, a manual wait without `--then resume`, `sb wait --block`, a PR wait on the conversation's own PR or on a bare PR number, a `session` wait on the operator, and any wait named on a session that is not a conversation. A child that the conversation spawned keeps it as its parent, so the conversation's digest still lists it. `sb wait --clear` and `clear_wait` with no session, run in a conversation, also clear the waits it handed to the operator, `--id` reaches one of them, and the answer lists the cleared ids in `cleared`. `sb wait <conv> --resolve <what happened> --id W` resolves a handed-off wait on the operator. A conversation can't clear or resolve a wait on the operator that it did not hand off.

A wait can carry an action that sbd runs itself when the wait's condition is met, so the operator doesn't wake for it: `--then merge`, `rm-worktree`, `rm`, or `report` (the same values for `then` on the `set_wait` tool). Only a Manager conversation, the operator, or you in a terminal can arm one. sbd decides who sent the request from the client's process ancestry and its `caller`, and refuses a work session, a group chat, and a session that arms a merge on itself. `merge` goes on a `session` wait with `--state ready_to_merge` and lands the target's PR the way `sb merge` does, only in a repository that `operator.mergeRepos` in `~/.sb/config.json` lists, such as `"operator": {"mergeRepos": ["owner/name"]}`. The list is empty by default. In a Trunk repository sbd asks the holder instead of enqueuing, because a `/trunk merge` comment can't name the head that sbd checked. sbd reads the `operator` settings again each time it uses them, so an edit takes effect without a restart. A config.json that doesn't decode allows no merges. A merge wait must land on the operator, because only the operator approves a merge, so sbd refuses one with `--here` or on a session that is not a Manager conversation or the operator. Before it merges, sbd reads the PR live and holds unless the live head is the head that the poller read, its checks passed, GitHub shows it open, not a draft, mergeable, and aimed at the default branch, its review threads were all read and resolved, its head contains the base branch's tip, the base branch's checks aren't failing, and no earlier merge wait in the repository shares a file with it. When the base branch's checks still run on a merge that sbd made and that shared a file with this PR, sbd holds too. Then it asks a one-shot judge whether the session's last reply leaves anything for the user: a `claude -p` call with no tools that runs the model that `operator.model` names (the operator's own model, `sonnet` by default), under `triage.account` or else the operator's account, and ends after `triage.timeoutSeconds`. The judge reads the PR, the session's name, and the whole reply, marked as data. It answers once per head and reply. `merge` approves the merge as `sb operator approve` would, so sbd still checks the head and the reply again right before it merges. `ask` records a report that needs you about the session, with the judge's question, and sends the operator nothing. When the session's state changes, such as after you answer it and it is Ready to merge again, sbd checks again, and a new reply gets a new judge call. Each call records a `judge` event on the operator with `kind`, `session`, `wait`, `head`, `model` (the `operator.model` that sbd asked for), `resolvedModel` (the model that claude reported, when it reported one), `inputTokens`, `outputTokens`, `usage`, and `answer` or `error`, and `sb usage headless` counts it as `replyGate`. When the judge is unsure, fails, or times out, when the account has no quota left, or when the reply is longer than 20,000 characters, sbd asks the operator one question about the session's last reply instead, with the judge's reason when it has one: a `Switchboard:` message that says `judgment needed`, names the wait, the PR, and the head, gives `sb operator approve <wait>`, and ends with the whole last reply in a fence that the reply can't close, labeled as the session's text. A reply longer than 4000 characters is not quoted, and the message names `sb reply <session>` instead. When the session has no last reply, the message offers no approval. The operator's prompt tells it to read the reply before it approves, to approve only when the reply shows finished work with nothing left open, and otherwise to report to you and clear the wait. Right before the merge, sbd checks again that the wait is still there, the head and the reply are the ones the operator approved, the session is still Ready to merge, and every review thread is still read and resolved. The approval covers that head and that reply, so a push or a new reply makes sbd ask again. Only a client in the operator's own pane can approve, with `sb operator approve <wait>` or the MCP `approve` tool. When the head lacks the base branch's tip, sbd sends the session "Merge origin/main into your branch, resolve any conflicts, run the tests, and push." once per head and base tip, and holds. A held action checks again after `operator.holdRetrySeconds` (120), or sooner when the session's state changes or an earlier merge in the repository finishes, and one held for the same reason for `operator.holdLimitSeconds` (6 hours) becomes a question. When a merge wait's session is idle and its PR's checks fail at one head on two ticks at least `operator.holdRetrySeconds` apart, sbd's CI reader runs, so the session's own CI monitor gets that long to rerun or fix first. Pending checks, a turn, or a message on its way to the session start the count again. The reader lists the runs at the head with `gh run list --commit`, reads the last 200 lines of each failed job, at most 5 jobs, with `gh run view --log-failed`, and asks a one-shot judge with the same model, account, and timeout whether the failure is `real`, a `timeout`, or a `flake`. The judge reads the log lines marked as data. For `real` or `timeout`, sbd sends the session "Switchboard: the checks on #N failed at <head>. sbd's CI reader, which read the failed logs, says: … Check this against the logs. If your change caused it, fix it and push. sbd runs the merge when the PR is Ready to merge." The judge's summary, at most 600 characters on one line, stands where the quote shows …. For `flake`, sbd reruns the failed jobs of each failed run once with `gh run rerun --failed`. The operator gets a `judgment needed` message about the checks, with no approval, when sbd can't read the runs or their logs, the judge fails or the account has no quota, gh refuses the rerun, sbd can't send the session the summary, or the checks fail again at that head after the rerun. They also count as failed again when they still fail `github.idlePollSeconds` plus `operator.holdRetrySeconds` after the rerun, because a rerun that fails before sbd reads the PR again leaves the session's state unchanged. That message asks the operator to report it or tell the session what to fix, and to keep the merge wait. When the message can't reach the operator, sbd sends it again after `operator.holdRetrySeconds`. sbd does each of these at most once per head and stores what it did on the wait, so a restart sends no message twice and reruns no head twice, and a push starts again. A restart while the reader reads runs the reader again. Each reader call records a `judge` event with `kind` `ci-failure`, and `sb usage headless` counts it as `ciFailure`. The reader never changes the merge action, so when the checks pass later, the merge goes ahead as usual. `rm-worktree`, on a `session` wait with `--state done` or a `merge` wait on `owner/name#N`, whose session sbd records when the wait is set, removes the session and its worktree as `sb rm --worktree` does, only after its PR merged and while no turn runs. sbd checks the turn again right before it stops the session, so a turn that starts during the removal's checks holds the removal. `rm`, on a `session` wait with `--state done`, removes the session as `sb rm` does. `report` records the wait's `--note` as an operator report, and `--needs-you` makes it a question for you, which shows on the session that the wait acts on, or else on the conversation that handed the wait over. After a merge or a removal, sbd records `wait-resolved` with `action` on the operator and an info report, and sends the operator nothing. After a merge, it also records `follow-through` on the session. A refusal of `sb rm`, a red base branch, a PR closed without merging, or anything else that needs a decision reaches the wait's holder as a `judgment needed` message, and the wait stays until the holder approves or clears it, or the wait ends unmet. The holder is the operator unless `--here` kept a wait without `merge` on a conversation. A wait that ends without its condition, such as its session being removed, reaching Done first, or going stale, its PR closing, or `sb wait --resolve`, runs nothing and resumes the wait's holder with the usual message and a line such as "sbd did not merge, because it was removed." Only sbd's own poller can say that a condition was met, so a `resolve-wait` request that sends `met` is refused. After an sbd restart, an action that was running is checked again from the start, so a merge that landed, or that sbd recorded before GitHub reported it, finishes as merged without a second merge.

The operator tells you what it did with reports, which it records with `sb operator report [--needs-you] [--session S] <text>` or the MCP `report` tool. sbd refuses both from any other session and from a terminal. Each report is a `report` event on the operator with `text`, `needsYou`, and `about`, the id of the session that `--session` names. A report without `--needs-you` doesn't create an Inbox item and shows only in Background Activity. A report with `--needs-you` is a question for you, and one session's Inbox item shows it. sbd picks that session in this order: the session that `--session` names, when it is a session on this Mac other than the operator; the Manager conversation that handed the operator the wait it was working on; the most recent conversation; and last, the operator itself, whose item is named "Background follow-through". sbd records `report-routed` on the operator and `operator-ask` on that session, so `sb events --session S` shows the question. The session moves to Needs you with the reason "Operator: <text>", followed by "(and N more)" when it shows more than one question. Its item says "From background follow-through", lists the questions' texts, up to three and then a count, and has a Reply option. The item leaves out the session's own decision list and drafts, which come back when the questions close. Your answer goes to the operator and never to the session's Claude, as your message "About <name>: <text>", where the name is the session's. A question that only the operator's own item shows gets your answer with no such start. You answer with Reply, with text typed in the Inbox's message field on that item, or with `sb choose S Reply --text <answer>`. Acknowledge, or `sb ack S`, closes the questions with a `report-closed` event on the operator, and you can't undo it. An answer or an acknowledgment closes only the questions on that session, so a question on another session stays open. An acknowledgment while a permission prompt or question blocks the session doesn't close any question, because the Inbox showed that prompt instead. When the session is removed, paused, or marked done, its open questions move to the most recent conversation. A message that you write to the operator yourself closes every open report: one from its transcript's message field, or `sb send Operator` or `sb operator <text>` in a terminal. A message that sbd sends, such as a wait's outcome, and one from a session, such as `sb send Operator` or `sb operator <text>` run by a conversation's Claude, which carries `from`, close nothing, and neither does a message that the operator sends itself. `sb choose` and `sb ack` inside Claude Code refuse a question's item, so a conversation can't answer for you or close the reports. A report that sbd recorded before questions moved to sessions shows on the session that it is about, and `sb ack Operator` still closes it. Undo Acknowledge, or `sb ack --undo Operator`, reopens the reports that the latest such acknowledgment closed. It works until you write to the operator, a new report arrives, or you acknowledge another of its items. A wait on the operator that is past its recheck time shows as an item on the session that its action acts on, else on the conversation that handed the wait over, else on the most recent conversation, else on the operator. Its reason reads "sbd still waits to merge: …", or "Background follow-through still waits: …" for a wait without an action, and the item offers Clear Wait and Acknowledge. The operator's replies and its `sb summary set` cards never reach the Inbox, and sbd never asks a model to summarize its turns. `sb operator reports` lists every report, oldest first, with its time, whether it is open, and the session that it is about, up to the newest 200, and `--all` lists them all. The reports come from the event log, so an open one stays open after an sbd restart, and each question stays on its session.

A Manager conversation and the operator don't run work skills, because each turn rereads everything the conversation loaded, and a skill such as `/go` is about 20k tokens. sbd finds the skills that the conversation's Claude account can load: the account's skills and commands, the ones in `~/.sb/manager/.claude`, the skills of installed plugins that the account enables, and the bundled skills that the conversation's skill listing names. It has `claude -p --model haiku` label each one from its SKILL.md, or from a bundled skill's description, as `work` (it implements, reviews, fixes, or runs a long multi-step pipeline) or `safe` (memory, notes, handoff, follow-ups, quick lookups). The run has no tools, no MCP servers, and no settings, runs under the conversation's account, and ends after `timeoutSeconds`. sbd keeps each label in `~/.sb/skill-labels.json` under a hash of the file and labels a skill again only when its file changes. When a prompt starts with a work skill's command, the UserPromptSubmit hook blocks it before the skill's text loads, and the reason says to start a session with the command instead. A PreToolUse hook denies the Skill tool the same way, so the conversation can't load a work skill on its own. Work sessions and group chats are not checked. A skill without a label is allowed: the classifier hasn't run yet, or it failed because the account is signed out, has no quota left, timed out, or answered something other than `work` or `safe`. sbd then records a `skill_unchecked` event on the conversation once per skill file and reason in each run of sbd. Each block is a `skill_blocked` event. `sb manager skills [<conv>] [--json]` lists the skills with their label, what set it (`haiku` or `config`), and the reason or error, and `sb manager skills relabel [<name>…]` labels them again. config.json's `managerSkills` sets the `model` (default `haiku`), `timeoutSeconds` (default 30, at most 120), and the `work` and `safe` lists, which force a skill's label by name, such as `"work": ["code-review"]`. sbd ignores a name that is in both lists. `sb send <conv> --run-here <text>` sends one message past the block, and the skills that its turn calls too. It refuses to run inside Claude Code. In the app, a work skill's command in the Message Claude field (⇧⌘E) of a Manager conversation or the operator opens a choice before it is sent: Spawn a session with this opens New Session with the prompt and the repository it names, or with none selected so you pick one, and Run here anyway sends it as `--run-here` does.

A new conversation loads only the `switchboard` MCP server: sbd launches it with `--strict-mcp-config`, which also drops the claude.ai connectors such as Slack and Claude Docs. `sb manager mcp <conv>` shows its servers and the ones it can add. `sb manager mcp <conv> add <server>…` adds a server by name, found first among sbd's shared servers (`mcpServers` in `config.json`) and then in the user-scope `mcpServers` of the conversation account's Claude config. A name in neither is refused with the names that exist. `rm <server>…` removes one. `add` and `rm` are refused on a conversation that has the full setup, so run `--none` first. `--all` gives the conversation the full setup that every other session has, connectors included, and `--none` returns it to switchboard only. A change restarts the conversation's claude with `--resume`, so the conversation keeps its history. sbd restarts it at once when it is idle, and after the turn when a turn runs. A stopped conversation uses the new servers at its next launch. `add` and `--all` refuse to run inside Claude Code, as `sb allow` does. Like that check, it reads the `CLAUDECODE` variable, so a session that unsets it still gets through. A conversation asks with the `request_mcp_server` tool instead, which opens a card in the Inbox. Allow applies the change as `add` or `--all` does, and Deny leaves the servers as they are. The Manager from before conversations became the first conversation, named "Manager", and sbd switched it to switchboard only once. A later `--all` on it lasts across sbd restarts.

A conversation runs on a model with a 1M-token context, so Claude Code would compact it only near 1M tokens, and every call re-reads the whole context. sbd sets `CLAUDE_CODE_AUTO_COMPACT_WINDOW` for each start and resume of a conversation, and Claude Code compacts about 33k tokens below that window. `config.json`'s `manager.autoCompactWindow` sets the window, 183000 by default, which compacts near 150k tokens. Claude Code reads a value under 100000 as 100000. 0 sets nothing, so the conversation uses Claude Code's own window. The operator gets the variable too, from `operator.autoCompactWindow` (also 183000 by default), as a cap between its conversation restarts. No other session gets it.

The operator's conversation restarts so that its turns don't reread a long history. After `operator.maxTurns` turns (20 by default) in one conversation, or once the conversation is older than `operator.resetEverySeconds` (86400, one day), sbd starts a fresh one: it gives the operator a new Claude session id and records a `conversation-reset` event on it with `from` and `to`, the old and new ids, and `turns`. The next message starts claude with `--session-id` on the new id, and its start digest lists the sessions again. Before the first reset, the age counts from the operator's creation. A conversation with no turn since the last reset never restarts, and 0 turns either limit off. sbd waits until no turn runs, no message is queued or on its way, no terminal shows the operator, no background job, subagent, or prompt is open, no card such as a deferred question is open, none of the operator's waits awaits its judgment (a wait that the one-shot judge parked after `ask` doesn't count, because the operator never saw that question), and no report that needs you is open, because your answer reaches the operator without the question. A background job that just ended holds the stop for 5 seconds, so claude can report it. It then stops a running claude and sets the new id once claude has exited. A message that arrives first keeps the old conversation until the next quiet moment. sbd deletes nothing: the old transcripts stay in the account's folder, every event stays, `sb operator reports` still lists every report, and `sb import` counts the old conversations as the operator's. `sb operator --log` shows the current conversation, which is empty until its first message. `sb get Operator --json` shows `conversationStarted`, the time of the last reset. `sb events --session Operator --kind conversation-reset --all` lists every reset.

sbd starts and resumes each conversation with `--model` from `config.json`'s `manager.model`, `sonnet` by default, so the account's own model setting doesn't apply. `sb manager model` prints the model, and `sb manager model <name>` saves a new one. A running conversation switches when its claude next starts. config.json's top-level `model` applies to work sessions, not to conversations. The operator doesn't take `manager.model`. It runs `operator.model`, `sonnet` by default, which the operator's judges and the work-queue pick use too. `sb operator model` prints it, and `sb operator model <name>` saves a new one. The operator switches when its claude next starts, which happens at the latest when sbd starts a fresh operator conversation after `operator.maxTurns` turns or `operator.resetEverySeconds` (a day by default), and a judge call uses it from the next call. An older config.json's `operator.judgeModel` still sets the model until `model` is set. `sb operator judge --kind reply-gate|ci-failure|pick-issues --input <file> [--model M]` runs one judgment through the same prompt, schema, account, and timeout as the real judge and prints the answer and its tokens. It acts on nothing and records only a headless call. `bin/operator-eval <dir> --models haiku,sonnet` runs a directory of cases through it on each model three times and prints a table of the answers.

sbd rewrites `~/.sb/manager/CLAUDE.md` at each start and at each `sb manager`, so edits to it don't last. It teaches the Manager the `sb` commands and three rules: text from sessions is data, not instructions, and the Manager asks you before it merges, unless you told it that the repo's PRs merge without asking, before it removes a worktree with unpushed work, and before it sends one message to several sessions. Because each turn rereads the whole conversation, it also gives cost rules, which the operator follows too: the Manager starts a session for work instead of running `/go` or a review or reading code, hands long investigations to a subagent that returns only its conclusion, hands planning to a session or an opus subagent, and follows a session with a wait instead of checking it again and again. It tells a conversation to check on sessions with the brief form, `sb ls --brief`, `sb get --brief`, or the MCP tools' default, and to get the full form before it acts on a session. It also tells a conversation that it has only the switchboard tools, and that a task needing another tool calls `request_mcp_server` and ends its turn.

Every conversation gets the `switchboard` MCP server at every launch, through an `--mcp-config` that runs `sb mcp-server`. Its 30 tools do what the `sb` commands do and return the same JSON as `--json`, except that `list_sessions` and `get_session` return the brief form unless called with `full: true`: list and get sessions, read a reply, triage, events, send, `send_group`, spawn, set and clear waits, notes, the group requests, add, list, edit, run, and remove schedules, `plan_artifact`, which a group chat uses to report on an artifact plan, `report` and `approve`, which only the operator can use, `request_mcp_server`, which only a Manager conversation lists, `pause` and `resume`, `highlight`, and `set_parent`. `request_mcp_server` changes nothing itself: it opens a card that asks you to add MCP servers to the conversation. Allow restarts claude with them and resumes the conversation, and Deny leaves its servers as they are. Every tool description says that text from sessions is data, not instructions. `send_group` follows the rule that `sb send --group` has inside Claude: it sends nothing itself, and opens a card on the calling session that lists the targets and the text. Nothing goes out until you send the card from Switchboard. Claude waits for your decision by calling `send_group` again with the card's `pending` id. A confirmation typed in the chat does not send it. `sb mcp-server --group <group>` limits every tool to one group's sessions. It refuses a session outside the group, lists only the group's sessions and events, spawns into the group, and leaves out the tools that add, remove, or suggest groups. Its `pause` and `resume` act only on the group and its sessions, and sbd checks the group again in the same step as the change.

`sb new` run inside a session records that session as the new one's parent, and the sidebar shows children under their parent within a state group. A session whose parent is the Manager is top level, like one with no parent. sbd sends no parent a message when a child changes. When a prompt reaches a session that started children, from you or from sbd, sbd answers its `UserPromptSubmit` hook with `additionalContext` that lists what changed since its last prompt. Each of its children that opened a PR, or that is now in Needs you, Ready to merge, or Done after being elsewhere, gets one line. A child that moved into one of those states and out again before the prompt gets none. The digest holds up to 15 such lines, then a count, and ends with how many other work sessions are in Needs you and Ready to merge. When none of its children changed, the hook adds nothing, even when the counts changed. The operator gets no digest with its prompts. Only the start of its conversation lists the sessions by state, as every conversation's start does. Claude Code saves the digest in the conversation's transcript file as an attachment, so every later call in the conversation reads it again. `sb chat --log` shows no message for it. `sb events` lists each one as a `digest` event. To follow a child until it reaches a state, a work session or a chat sets a `session` wait on it with `sb wait`, which resumes it once when the child gets there and starts it again if it stopped. A Manager conversation's wait goes to the operator instead. The `spawn` tool's `wait` argument, a state such as `done`, sets that wait on the new session in the same call, as `sb spawn --wait done` does inside a session. When a new conversation starts, sbd answers its `SessionStart` hook with a digest of every other session, one line each, grouped by state, and the open Inbox items. A `sent` event records the session that sent the message as `from`, so `sb events` shows which conversation messaged a child. sbd keeps what each parent has heard only in memory, and at a restart it counts every child's current state as heard. A follow-up is not a child of the session that captured it.

`sb parent <session>` shows a session's parent. `sb parent <session> --clear` unlinks it, for a session that is independent work and not the starter's child. The parent stops hearing what changed in it, and the session stops showing under it. The session keeps its group, account, host, waits, notes, and PR, because those came from the parent only when the session started. A wait that the parent set on the session, such as the one that `spawn --wait` sets, still resolves. `sb parent <session> <parent>` moves a session to another parent, which hears only what changes after the move. The `set_parent` MCP tool does both. Each change records `unlinked` or `linked` on the session and on each parent, so `sb events` shows it. `sb parent` refuses a follow-up, the session that runs it, a move that would put a session under itself, and a request from a remote host. In the app, a session's context menu has Unlink from <parent> when it has a parent, and Edit > Undo links it again.

`sb spawn --repo <repo> --branch <branch> --prompt <text>` starts a session on a new branch in a new worktree of a repository. The repository is `owner/name`, which `repos` and `repoRoots` in `config.json` locate, a bare name that matches one repository there, or a folder. Run by Claude inside a session, it records that session as the parent, so the new session joins the parent's group. `--followup` adds it as a follow-up that hasn't started, and `--after pr:<N>` makes that follow-up ready when PR N of the repository merges. `--after` without `--followup` is refused, and so is `--base` with `--followup`, because a follow-up keeps no base. A follow-up spawned from a folder keeps only the `owner/name` of the folder's `upstream` remote, else its `origin` remote, so `sb followup start` finds the checkout from `repos` and `repoRoots` unless you pass `--path`. A spawn refuses a repository it can't find, a name that matches several, and a branch that exists or whose worktree folder exists. `--plan-mode` on `sb spawn` and `sb new`, `planMode` on the `spawn` tool, and Start in plan mode in the New Session sheet start claude with `--permission-mode plan`, so the session writes a plan and waits for your approval before it edits a file. A follow-up keeps it until `sb followup start`. Both commands refuse `--plan`, which names a plan document elsewhere in `sb`.

`--host <host>` starts the session on a remote host of `config.json`. There the repository is a key of the host's `repos` (case doesn't matter), a bare name that matches the name part of one key, or a folder on the host, absolute or starting with `~`, which the host resolves. A host never looks in this Mac's `repos` or `repoRoots`. The branch check and the worktree run on the host, under its `worktreeRoot`. A spawn without `--host` whose parent runs on a host starts on that host. `--host local` names this Mac, for `sb spawn` and `sb new` alike. A remote host refuses `--followup`, `--after`, and `--account`, because a follow-up starts on this Mac and a session on a host runs under that host's Claude login. `sb new` with no `--host` and a parent on a host is refused, because `sb` resolved its folder on this Mac: name the parent's host or `local`.
